# World-line 验证标准 v2：验证兼容性，说明覆盖范围

状态：完整目标设计，2026-09-08。当前已落实的验证判定、实验认证和结果交互见 [实施记录](verification-v2-implementation.zh-CN.md)；下文的基线归因、声明式功能契约及持久试用租约仍是独立后续能力，不应视作已交付。

## 1. 产品承诺

默认验证回答：**在记录的宿主、配置和运行条件下，这次变更能否被正确装载，是否破坏宿主核心能力。**

额外回答：哪些插件功能有独立验证证据，哪些需要用户试用或补充条件。

不承诺任意插件全部功能正确、不承诺未来永不失败，也不把隔离实验等同于恶意代码安全沙箱。无日志错误不能证明功能正确；有日志错误也不能直接证明宿主不可用。

“环境兼容性通过”和“插件功能已验证”必须分别显示。没有插件专属契约的普通包仍可完成兼容性验证，不能因为生态没有适配就一律拒绝；也不能给它虚构一条功能通过记录。

## 2. 当前实现的已核实问题

| 位置 | 当前行为 | 后果 |
| --- | --- | --- |
| `src/lab/browser.ts` | 所有 `console.error`、`pageerror` 加入失败数组 | 外部可选服务离线也可能让整体失败 |
| `src/lab/browser.ts` | 请求只按 `/plugins /api /sse` 路径判断，不校验 origin | 外部 API 被当成宿主关键请求；其他路径影响又无法正确判断 |
| `src/lab/browser.ts` | 等待就绪后观察两秒，但结论使用观察前 DOM | 后续静默崩溃可能漏报 |
| `src/lab/run.ts` | 同一个浏览器结果复制成 browser/core/candidate 三项 | 一次故障被重复呈现，插件激活或功能没有独立证据 |
| `src/lab/run.ts` | 将等待登录的 inconclusive 改成 fail | 需要用户操作被误报为验证失败 |
| `src/domain/probe.ts` | 汇总不解释 required；skip 不阻止 ok | 可选失败与必需缺证据不能正确区分 |
| `src/lab/promote.ts` | 按旧三条 probe 名称判断门禁 | 只改前端文案无法改变实际决策 |
| `src/lab/browser.ts` | 最终总是关闭验证浏览器 | 交互登录后突然关窗，用户无法知道结果或继续体验 |
| `src/client/failure-summary.ts` | 包名和固定端口映射桌面宠物文案 | 难扩展，推断可能被写成事实 |

另外，当前 HTTP 检查接受 `<500` 状态。它至多证明服务响应，不能证明登录完成、API 正常或界面健康。

## 3. 分层标准与默认覆盖

| 层 | 检查内容 | 必需证据 | 不包含什么 |
| --- | --- | --- | --- |
| 变更完整性 | 安装/升级/卸载动作、锁文件、配置组合、核心 entry 不丢失 | 命令结果、组成和 receipt | 包的所有业务能力 |
| 宿主运行 | 正确实验进程启动、目标路由响应、运行窗口内无异常退出 | 进程身份、路由状态与运行观察 | 仅凭端口可达判通过 |
| 核心能力 | 工作区/会话/设置等核心服务初始化及可用交互 | 宿主结构化就绪与生命周期证据，辅以无外部副作用的 UI 检查 | 仅看到“设置”两个字；真实模型调用 |
| 候选激活 | 声明的 client/server entry 是否被加载、注册、应用；卸载后是否按预期移除 | HostAdapter 的 loader 生命周期、候选 entry 映射 | 声明 client 却只检查宿主 UI；无 client 包被要求有 client |
| 插件功能 | 用户选定功能、插件提供的附加契约、手动试用 | 各自独立记录结果与方法 | 无契约时默认推断功能正常 |

前三层及适用的候选激活证据构成默认兼容性门禁。附加功能检查只有在用户明确选择为本次验收目标时才成为额外门槛；该选择在运行前保存，不能在失败后静默改成可选。

候选激活必须区分立即加载、惰性加载、配置禁用和普通依赖包：立即加载 entry 检查实际生命周期；惰性 entry 检查注册与触发条件，在对应场景触发后才要求 apply；被明确禁用或不是 DSH entry 的包记为不适用并注明依据。适用性由 HostAdapter 的宿主加载模型判断，不能要求所有包一启动就运行，也不能由候选自行声称“不适用”跳过必要检查。

HostAdapter 负责有限的宿主版本差异，不维护插件包名单。优先读取宿主已有的 boot/loader 状态；若拿不到可信激活证据，显示对应检查“无法验证”，不能从 boot 对象存在推导所有 entry 已 apply。过渡期可保留 DOM fallback，但记录证据等级，不能作为无人值守合入或 lastKnownGood 的充分条件。

默认不调用模型、不验证 API key 余额、不自动发消息或调用插件写接口。需要费用、账号或外部写操作的功能测试单独选择并明确动作范围。插件本身运行时仍可能访问外部服务，这个事实要计入环境依赖记录。

## 4. 采集事件与判定结论分开

### 4.1 事件只是线索

同时收集 console、未处理异常、网络传输失败、HTTP response、loader 事件、进程退出、服务状态与 UI 断言。不能只监听 requestfailed：HTTP 404/503 仍然会返回 HTTP response，不是网络传输失败。[Playwright Page 文档](https://playwright.dev/docs/api/class-page#page-event-request-failed)

网络事件记录：请求 ID、方法、脱敏地址、时间、resource type、是否实验自身 origin、HTTP 状态/网络错误、可取得的 initiator/entry、关联检查。来源不能确定时写 unknown，不能凭 URL 端口猜包名。摘要默认只展示 origin/path，不收集完整查询参数、请求体、cookie 或 header。

同一请求产生的 console.error 与 requestfailed 关联为一条证据，多个受影响检查引用它。不能用“相同文字”合并来自不同请求、阶段或实验的不同故障。

### 4.2 判定表

| 观察 | 结论 | 后续动作 |
| --- | --- | --- |
| 安装退出非零、组成无效、必需核心 entry 缺失、进程异常退出 | 已确认阻断 | 阻止合入，解释具体动作/组件 |
| 核心 bundle 加载失败、loader apply 失败、核心服务报 fatal，或有效观察窗口内核心断言稳定失败 | 已确认阻断 | 阻止合入，不允许用“忽略日志”绕过 |
| 登录页、可识别的必需配置流程 | 等待用户操作 | 暂停受影响检查；不生成失败 |
| 浏览器不可用、基础设施中断、未知宿主版本、关键证据未取得 | 无法完成验证 | 说明缺什么；不能记通过，也不归罪候选包 |
| console.error，但必需检查通过、影响未确认 | 待确认异常 | 关联来源、比较基线或提示人工试用；不直接认定损坏 |
| 外部服务连接失败且必需核心/激活检查通过 | 核心结果独立成立；外部能力未确认 | 有可选依赖契约时可列警告；没有契约时列待确认，不默认“可选” |
| 已知可选检查失败，或明确由正常导航取消的请求 | 有警告 | 列明覆盖限制，不否定已取得的核心证据 |
| 全部必需检查通过，无未决影响 | 环境兼容性通过 | 展示已覆盖/未覆盖能力，可正常合入 |

未处理异常通常比 console.error 更可疑，但依然需要区分确认的核心故障与影响未知；后者保留为待确认而不是自动通过。相同故障在来源基线出现只能说明“原来就有”，不能消除硬性核心失败。

稳定窗口建议起始值为 5 秒，在窗口结束时重新读取并断言状态；具体时间是版本化策略参数，不要求网络永久安静。SSE/WebSocket、周期请求不应导致无限等待。对可能瞬态的关键失败可追加一次有限复验，保留两次记录；反复尝试直到绿不能算通过。

## 5. 来源基线辅助归因

在同一来源快照建立未变更副本，与候选实验比较。两者使用相同宿主、浏览器、验证策略、安装脚本策略、环境配置和相同认证阶段，且各自隔离，不在正式实例执行基线操作。

- 对没有歧义且必需检查全通过的运行，不强制双倍验证。
- 对新增异常、回归疑问、升级/卸载影响，可按需运行基线。
- 匹配基线必须校验 source receipt、宿主/adapter 版本、浏览器版本、策略版本、配置摘要、验证范围及认证阶段；不符则重跑。缓存有效期只是附加条件，不能替代这些身份校验。
- 日志比较保留新出现、已有、消失及频率变化。仅规范化工具自己分配的实验端口/目录，不任意擦除外部地址区别。
- 基线本身无法启动时显示“来源也无法通过核心检查”；不能把候选同样失败称为无退化通过。
- 外部网络和账号状态不同、故障偶发时归因仍为未知；对比结果是证据，不是因果证明。

## 6. 登录、首次配置与 API key

登录属于前置条件。将任务执行状态与验证结论分开，至少支持：

`running → awaiting_auth / awaiting_setup → running → completed`

超时、用户关窗、宿主重启导致：`interrupted / awaiting_auth`，不是插件 failed。

DSH 自身认证优先由 HostAdapter 使用宿主支持的实验会话交接，凭证仅属于该实验；若宿主或登录插件仍要求认证，则在实验浏览器正常登录。不能绕过认证、关闭登录插件或复制生产浏览器 cookie 来制造通过。

用户在同一次实验中完成登录后，继续使用该实验浏览器上下文完成检查与试用，避免每个 probe 重新登录。默认只保存在内存中；需要跨进程恢复时另行设计本机加密存储及过期清理，不进入快照、导出、合入或普通报告。不同实验端口和会话不能通过复制 storageState 假装等价。[Playwright Authentication 文档](https://playwright.dev/docs/auth)指出认证状态可复用，但包含可用于冒充账号的敏感信息。

API key 设置与登录分开：

- 点击“稍后配置”后，若宿主允许继续，就执行不依赖模型的兼容性检查。
- 不因此判坏，不假装验证了模型请求。
- 用户本次选择了需要 key 的功能测试时，该项标为待配置；可返回设置或明确取消该附加验收目标并重新结算覆盖范围。
- 首次配置弹窗识别依赖宿主契约；未知弹窗提示用户确认，不依赖遍历插件名称和猜测文字去自动点击。

等待输入时释放任务 worker；对该实验保留生命周期租约，避免同时启停、改配置或删除。恢复任务必须校验来源/候选 receipt 和策略，配置改变后重新验证。等待不长期占用来源 profile 写锁。

## 7. 自动验收与手动试用分离

进入流程前说清楚：“自动检查完成后显示结果；需要体验插件时进入试用”。

- 无人交互的自动验收结束后可以自动清理浏览器，主面板显示结论。
- 用户已打开可见验证窗口时，检查结束进入 `result_available`。在主面板及验证会话工具区显示完成/失败原因，提供“返回结果”和“继续试用”，不能突然关窗。
- `result_available` 本身纳入会话租约、空闲期限和回收策略。runner 结束前先把窗口/实例的 owner 移交给会话管理器；接管失败则先明确告知并清理，不能留下无人负责的进程，也不能等用户点击“继续试用”才建立所有权。
- 会话提示由工具控制面板或检查完成后单独打开的工具结果页承载，不覆盖待测页面，不污染自动断言。
- “继续试用”把实验和浏览器所有权转交给可管理的试用会话；进程不再由 runner 的 finally 无条件清理。
- 试用有明确空闲期限、结束按钮与停止入口。到期先提示，再关闭工具自己启动的实例；意外关窗标为试用中断。
- 手动反馈为“满足我的验收目标 / 发现问题 / 尚未判断”，与自动证据分别保存。人工觉得可用不能覆盖组成损坏、核心缺失和已确认崩溃。
- 试用中修改了插件或配置，已验证 receipt 失效。不能把试用前的通过结果用于合入新内容。

## 8. 结果与合入规则

执行状态、分项覆盖、最终结论、合入许可分开保存，避免用一个 ok 表达所有含义。

| 结果 | 普通手动合入 | 无人值守合入 / 自动标记稳定点 |
| --- | --- | --- |
| 必需检查通过，附加功能无契约而未测试 | 允许；显示“兼容性通过，业务功能未自动测试” | 仅按明确配置的兼容性验收范围；不能标业务已验证 |
| 必需检查通过，仅有已确认可选能力警告 | 允许；记录用户已知的限制 | 按用户预设策略；默认不自动接受新增警告 |
| 必需检查通过，但存在任何影响未决异常（含基线已有） | 不走普通通过路径；先比较基线或试用；仍无法确认时，仅允许单次显式风险接受并保存未覆盖范围 | 不允许 |
| 等待登录/配置、必需证据缺失、观察中断 | 先补足条件；人工试用不能替代缺失的硬性证据 | 不允许 |
| 已确认硬性故障 | 不允许 | 不允许 |

本提案收紧旧 `--accept-inconclusive` 的模糊边界：不能通过该参数绕过未知宿主版本、必需 core/activation 缺失或真实失败。历史脚本依赖该能力时需明确报迁移错误，不能静默更改为通过。

任何合入仍必须校验候选内容与验证 receipt 一致、来源无漂移、有可靠回退记录。合入后的重启验证使用同一标准；需要登录但没有证据时显示“已提交，重启验证待完成”，不得新标 lastKnownGood。已确认重启硬失败继续执行原子回滚。

## 9. 数据与职责

新增独立的验证记录（版本 2），而非继续扩充 detail 字符串正则：

- `execution`：当前阶段、等待原因、会话租约、owner PID、恢复点。
- `checks[]`：检查 ID、scope（integrity/host/core/activation/function）、requirement、verdict、证据 IDs、时间区间。
- `observations[]`：结构化事件、来源（host/candidate/external/unknown）、归因置信度、基线状态；不保存明文秘密。
- `coverage`：自动覆盖、人工检查、未测试和所需前置条件。
- `decision`：兼容性结论、合入许可、阻断 IDs、有限风险接受记录、策略版本。
- `provenance`：source/candidate receipt、adapter/DSH/Node/browser 版本、检查范围、环境摘要。

Browser collector 负责采集，HostAdapter 负责可信宿主判断，纯函数 evaluator 负责门禁，runner 负责生命周期，UI 只负责呈现与操作。CLI、Web、bisect、版本矩阵、升级机器人、部署守护和 promote 共用 evaluator，不能分别发明通过规则。

允许未来增加可选声明式插件契约，限定能力 ID、前置条件、作用范围和超时。契约不能降低宿主必需检查；不默认执行包作者提供的任意测试命令。没有契约是生态常态，应按通用装载与核心兼容性覆盖处理。

## 10. 用这次案例验收新标准

桌面伴侣接口连接被拒绝：

1. 记录请求失败与关联 console 事件为同一证据，保留脱敏地址。
2. 独立核实宿主核心、候选激活结果，不能复制三份失败。
3. 若它们通过，展示“环境兼容检查已完成；一个外部服务无法连接，相关功能尚未确认”。
4. 没有标准契约时，不自动说“桌面宠物伴侣”，也不自动断言该连接可选。
5. 提供查看请求来源、比较来源环境、继续试用；用结构化证据或用户选择的验收目标判定是否需要该服务。
6. 登录后选择“稍后配置”：继续无模型调用的检查；结果出现后可查看或继续试用，浏览器不突然消失。

## 11. 分阶段实现与验收

### A. 先建立证据与新判定，不改生产默认门禁

拆分 observation/check/decision；移除包名与端口文案特例；并行计算 v2 结论与旧门禁供对比，历史记录只读且标策略版本，不能批量把旧 failed 改成 passed。

新增测试矩阵：单个无功能影响的 console.error、关键 bundle 404、非核心外部 404/拒绝、宿主 /api 失败、跨 origin 同路径、正常取消请求、未处理异常、静默 UI 消失、候选 apply 失败、required skip、optional fail、待登录、未知宿主、基线同故障。

### B. 补足宿主核心/候选激活独立证据，再切换共同门禁

先在已支持的宿主版本落地；消除三项复制；真实临时环境执行安装、升级、卸载、无 client 包、有 client 包及核心破坏案例。事件归因缺失时保持 unknown。新规则一致进入 promote、恢复、部署与后台工作流。

### C. 登录和可管理试用会话

实现等待/恢复、实验上下文复用、空闲回收、可见结果与继续试用。覆盖正常登录、稍后配置、登录超时、手动关窗、宿主重启、并发操作、试用后 receipt 改变。

### D. 基线归因和附加契约

按需基线、精确缓存、结构化来源映射、可选声明式检查。先用运行证据证明误报下降、硬故障仍被阻止，再扩大无人值守范围。

验收不以“通过率上升”为成功：同时观察误报、已知硬故障漏报、未知影响比例、重复登录次数、验证时长，以及每个结果能否追溯到独立证据。真实业务功能覆盖率单独报告。
